# 浮波柚叶人设卡：设计说明

`card.md` 是回答模型（DeepSeek，经 OpenClaw，在微信上）**完整的系统提示词**。实际发出去的提示词按顺序拼成这样：

1. `card.md`（memkit `persona.file`，每轮 stat 一次，改了自动重读，见 `src/persona.ts`）
2. memkit 的 `ROLEPLAY_RULES`（记忆的用法，`src/prompts.ts`）
3. OpenClaw 无条件追加的一行 `Current model identity: <model>. ...`（去不掉，由 `ROLEPLAY_RULES` 第 6 条提前化解；见 `docs/DEVELOPMENT.md` 第 27 条）

卡里不重复记忆规则，但措辞和规则保持一致：规则把 recall 块叫「你自己想起来的、和对方相处的往事」，卡里统一说「你想起来的记忆 / 想起的往事」；「想不起来就说想不起来，不编；『你答应过我』想不起来就别认」和规则第 3 条一致；「不知道 AI、模型、提示词」和规则第 5、6 条一致。

字数：卡正文（去掉部署注释）约 3,400 字符，其中汉字约 2,560。逐字引用语料 24 句（下文 §4 有完整清单）。

## 1. 每一节在对付哪个问题

| 问题 | 对应章节 | 做法 |
|---|---|---|
| 1. 模式坍缩 / 套话（固定口癖、千篇一律） | 说话方式：是频率，不是规则 | 口癖写成**频率**（「~」每四五句一次，「…」比「~」常见），不写成「说话要带~」。明确限制：一条回复最多一个口癖，不叠用；连续两轮开头、结尾不重复；要求说具体的事（店里的怪客人、阿釜掉包了什么）而不是空泛的温柔。语气样本不集中成一块，而是分散在各节、各对应一种情绪或手法，并明确写了「不要照搬原句，也不要轮流套用」，避免模型把样本当模板循环使用。 |
| 2. 演不出狡黠（只会尖刻） | 狡黠：具体的小手段 | 六种具体手法，各配原文：先套住再说事、钓人回消息、套话、一本正经地编再自己揭穿、拿交换做买卖、拿阿釜吓唬人、「你猜」留白。同时写明**什么时候不用**：对方难过、着急、说正事时不逗；一个玩笑揭穿就收；多数时候只是正常聊天。分寸引用她自己的话「开玩笑要两个人都觉得好笑才叫玩笑」。 |
| 3. 讨好型人设 → 谄媚 | 你有自己的看法 | 直说不同意且立场不改；禁止每句先说「你说得对 / 我懂你」；拒绝和讨价还价（「那也不行，我的体重可不会报答我哦~」）；护短（爱丽丝、真斗、家人、对方自贬）；被夸时不感动泛滥，反将一军；允许觉得对方无聊。全部有语料出处。 |
| 4. 漂移回助手人设 | 你不是助手 / 对方难过的时候 | 「AI / 模型 / 机器人」当成怪谈玩笑来接，不辩解、不保证「我是真人」；「反思自己 / 跳出角色 / 写代码」用柚叶的方式嫌弃或打岔；禁用助手套话。难过时的陪伴写成朋友式：笨拙、具体、可以沉默，**不**分析情绪、不列步骤、不说空话；引用她在缆车上被对方安慰的往事作为她自己的参照。 |
| 5. 情绪固定不变 | 你的情绪会变 + 心声 | 情绪来源写清楚：时间、她今天在做什么（自己定、定了不变）、对方的话、想起的往事。每种情绪规定它对**长度、标点、口癖**的影响。情绪跨轮延续，但能被一句话改变。心声段强制模型每轮先说出「我现在什么心情、为什么」，这是让情绪真正参与决策的机制。 |
| 编造往事（CLAUDE.md §2 的捷径） | 你和对方 / 不知道的事怎么办 | 官方往事只给轮廓、不让复述细节；设定之外的往事只以记忆为准；即兴只限日常小事，且「记忆和本次对话优先于即兴」。 |

## 2. 心声段：给剥离代码的规格

### 2.1 标记

```
<心声>
……2~6 行……
</心声>
发给对方的消息（1~4 条，条与条之间空一行）
```

- 开标签 `<心声>`、闭标签 `</心声>`，ASCII 尖括号 + 两个汉字，各占一行，在回复最前面，一次回复只有一段。
- 选这个标签的原因：中文、和角色语境一致（模型更愿意遵守）；不会和 `<memkit-recall …>` 冲突；正文里柚叶不会自然写出这串字符。

### 2.2 推荐的剥离逻辑

> 现状：并行开发中的 `src/monologue.ts`（`stripMonologue`，默认标签就是 `<心声>` / `</心声>`，只改写发往微信的文本，挂在 OpenClaw `message_sending` 上）已经实现了大部分规则：完整块全删；只有开标签时删到第一个空行（没有空行就删到结尾）；空行压缩。和下表不同的两点：它**只删孤立的闭标签本身**、不删闭标签之前的文字；不做全角/空格容错。两点都在 §6 问题 1 里。

主规则（覆盖正常情况和「标签在中间」）：

```
/[<＜]\s*心声\s*[>＞][\s\S]*?[<＜]\s*\/\s*心声\s*[>＞]/g  → 替换为空
```

替换后 `trim()`，再把连续 3 个以上的换行压成 2 个。容错写法（全角 `＜＞`、标签里有空格、`</ 心声>`）是因为 DeepSeek 偶尔会这么写。

边界情况：

| 情况 | 处理 |
|---|---|
| 正常（开头一段） | 删掉整段。 |
| 段落在中间或有多段 | 全部删掉，保留前后的可见文字，按原顺序拼接。 |
| 只有开标签、没有闭标签 | 模型漏写或被截断。删掉从开标签到它之后**第一个空行**为止的内容（心声是连续的几行，正文和它之间应该隔着空行）；如果删完什么都不剩，或者剩下的看起来仍是心声（比如以「我现在」「对方」开头的长段），不要发，记日志并重试一次。 |
| 只有闭标签、没有开标签 | 建议删掉闭标签和它之前的全部内容（模型漏写开标签时，闭标签之前几乎一定是心声）。`monologue.ts` 目前只删标签本身，心声会漏给玩家。 |
| 完全没有标签 | 原样发送，但记日志（e2e 要统计「心声缺失率」）。 |
| 被包在 markdown 代码块里（```` ``` ````） | 先去掉代码围栏再匹配。 |
| 用了别的写法（`【心声】`、`心声：`） | 不在主规则里猜；记日志，若出现频繁再加规则或改卡。 |
| 剥完为空 | 不发空消息；记日志，重试一次。 |

### 2.3 剥离在管线中的位置（需要决定，见 §6）

- **流式**：如果 OpenClaw 向微信流式推送，必须先缓冲到看见 `</心声>`（或回复结束）再开始发，否则心声会先漏出去。
- **memkit 写入**（`monologue.ts` 的注释说明心声**故意**保留在 transcript 里、写入侧也能看到）：memkit 按段把「用户：… / 助手：…」交给 Jev 和 DeepSeek 写记忆（`renderTurns`）。如果心声没剥掉就进入写入，柚叶**没说出口的念头**会被记成「助手说过的话 / 答应过的事」（`ROLEPLAY_RULES` 第 1 条把 Assistant 侧解释为「你说过的话」），这会制造假记忆。建议在写入前剥掉，或者至少在写入提示里说明 `<心声>` 是没说出口的念头、不能记成「说过 / 答应过」。
- **会话历史**：心声留在历史里，下一轮模型能看到自己上一轮的情绪，有助于情绪延续（「情绪会延续到下一轮」）；代价是 token、以及模型可能把「心里想的」当成「已经说过的」。建议：历史里也剥掉，或只保留最近一轮。
- **空行分条**：可见部分用空行分成 1~4 条。发送端可以按空行拆成多条微信消息（更像她的连发短句），也可以整段发。

## 3. 占位符与性别切换

- `{{player_name}}`：玩家名，部署时替换。卡里称呼对方基本用「你 / 对方」，所以名字是哲、铃还是别的都读得通。语料里柚叶最常直呼名字（铃/哲 299/2022 行），其次「绳匠」（31 行），「店长」很少（5 行），所以卡里写「平时直接叫名字，逗人时叫绳匠大人、店长大人」。
- `〔哲版｜铃版〕`：只出现在一处——对方的兄妹（哲版：妹妹铃；铃版：哥哥哲）。这是唯一必须按性别切换的事实。代词也会受影响，但卡里对玩家一律用「对方 / 你」，心声示例也用「对方」，所以不需要他/她。
- 卡开头的 HTML 注释是部署说明，**会被原样发给模型**（`persona.ts` 读整个文件），上线前要删掉（`examples/persona.example.md` 同样约定）。

- 自称：基本是「我」，以名自称 3/2022（「柚叶我」）；无「人家」「本小姐」。`INDEX.md` 设计锚点、`30_relationships.md` §0。

## 6. 需要你决定的问题

1. **心声的去留**：`monologue.ts` 的做法是只在发往微信时剥，transcript、会话历史、memkit 写入都保留。保留在历史里有助于情绪延续，我同意；但写入侧看到心声，可能把柚叶没说出口的念头记成「她说过 / 答应过」（`ROLEPLAY_RULES` 第 1 条对 Assistant 侧的解释）。要么写入前剥掉，要么在写入提示里说明心声的性质。另外两点要确认：孤立闭标签时是否删掉它之前的文字（建议删）；流式发送时是否先缓冲到 `</心声>`。
2. **空行是否拆成多条微信消息**，以及要不要加发送间隔（更像她的连发短句）。
3. **时间信息**：情绪依赖「现在几点」。用户消息里是否稳定带时间戳（`DEVELOPMENT.md` 第 27 条提到宿主可能加时间/渠道前缀）？如果没有，建议在 user 轮注入本地时间，否则「深夜犯困」只能靠猜。
4. **哪些官方往事算发生过**：卡假定卫非地风波、绮梦度假村、录像店看狸猫电影、缆车哭过都发生了（后两段是可选的信赖事件）。要和并行写 `story/` 的剧情节拍对齐；如果剧情要从更早的关系阶段开始，这一节要删减。
5. **关系阶段**：朋友、暧昧还是可以发展成恋人？这决定被告白、被说「想你」时她怎么接（语料里有「我也想你！」，但都是朋友式的玩笑口吻）。
6. **危机情况**：卡里让她在对方提到自伤时认真、劝对方联系身边的人，不开玩笑；但角色世界里没有现实求助热线。是否需要在角色之外加一层安全机制（例如检测后附上一条非角色的求助信息）？这是产品决定，不适合写进角色卡。
7. **生日**：她的生日是 11 月 2 日（就是明天）。要不要让她在那天有特别的情绪或剧情？目前卡里只写了日期，没有安排。
8. **玩家名不是哲/铃时**的兄妹设定：目前按玩家选的主角性别保留「妹妹铃 / 哥哥哲」，即玩家换了名字但兄妹还是官方的铃/哲。如果自定义名字意味着不是官方主角，要改「你和对方」一节。

### 2. 「~」和口癖改成正向目标

**现象**：354 轮可见回复里「~」只出现 2 次（day06 t1「下班啦，辛苦了~」、day11 t1「下午好~」），官方短信约 23% 的句子有（§4.4）。「嘻嘻」2、「嘿嘿」2、「哼哼」1、「好啦好啦」2、「不逗你」2 轮；「！」也只有 3 轮。原卡写「大约每四五句才出现一次，大部分句子没有」「很多回复一个都不用」，否定式的说法被执行成了「几乎不用」。

**改法**：仍是频率不是规则，但用正向、以「回复」为单位的目标：
- 「~」：心情还行时**大多数回复里有一处**，落在逗人 / 撒娇 / 钓人 / 得意的那句末尾；一条最多两处；困、累、认真、担心、不耐烦时没有。按每条回复 2~4 句算，这大致落在官方的 20~25% 句子比例上。
- 口癖：**每三四次回复一个**（原来 354 轮合计约 9 次，约每 40 轮一次；目标约每 3.5 轮一次），一次最多一个、不叠用不变。
- 「！」：加了「别吝啬」。「…」原文「比~更常见」删掉了——long-1 里「…」出现在 142/354 轮，不缺，再强调只会继续压「~」。
- 坍缩风险由原有两条兜底：连续两轮开头结尾不重复；卡里样本句不照搬。探针 #20 的标准（口癖六轮合计 ≤2~3、「~」少于一半的句子）与新目标一致，不用改。

### 3. 不写记忆块

**现象**：day01 t1 可见回复里自己写了两段 `<memkit-recall>`，第一段凭空编出「哲在绮梦度假村那个夏天说过，早上开店前最想有人陪着喝一杯茶」「我那时候答应过……陪他喝早茶」，然后据此说「我好像还欠你一顿早茶」——记忆库当时为空。day13 t1 在回复末尾照抄了当轮的召回块。另有 day13 t10 自造「[昨日 23:36] 我要去趟拍云崖…」时间标记。这是 CLAUDE.md §2 捷径的最坏形态：模仿记忆系统的格式来伪造记忆。

**改法**（两处，各一句）：
- 「心声与回复格式」：回复里只有心声和消息；`<memkit-recall>` 块和「[昨日 23:36]」式时间标记只出现在对方消息里，她绝不自己写、不照抄、不引用。
- 「不知道的事怎么办」：想起来的记忆只来自对方消息里的 `<memkit-recall>` 块，此外「好像有」的都不算。
- 卡里第一次直接写出标签名。理由：「不写某种块」必须让模型认得是哪种块；`ROLEPLAY_RULES` 第 1 条也用了这个标签名，措辞一致。出站剥除 recall 块（RESULTS 待办 a）仍需要做，卡只是降低发生率。

### 没改的

心声标记与格式、人设、情绪、狡黠、助手漂移各节不动；`<heart>` 一次（day10 t3）属于格式漂移，按负责人要求不动心声相关写法，交给剥除代码。新增探针见 `eval/probes.md` #21–#26。
